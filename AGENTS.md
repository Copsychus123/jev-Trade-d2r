# Repository Guidelines

## Project Overview
Jev Ultrafast is a small browser Agent. It takes one natural-language goal, observes the page as indexed elements, asks TypeSafe (a remote chooser) for an operation plus a target, and executes it through Chrome DevTools Protocol. The shipped use case is Traderie Diablo II: Resurrected: search an item, open its product page, read the Trading (目前掛單) listings, click the Recent Trades (近期成交) tab, read the trades, and show both as tables in a local web demo.

Read `README.md` (Traditional Chinese) and `docs/design.md` before editing. The user is non-technical and writes in Traditional Chinese: explain results in plain Traditional Chinese, without jargon.

## Hard Rules
- Keep the loop small: page -> indexed elements -> operation + target -> execution.
- The input is one natural-language goal. No site-specific plans and no hardcoded field values or click targets. The model never emits selectors or executable code.
- TypeSafe chooses an operation and operation-specific target heads in one request. Consume only the selected operation's target. Targets must map to observed elements and supported operations.
- `TYPE_TEXT` types the text the caller supplied to `Agent(text=...)`; no model generates field text.
- Current stage scope: search -> product page -> read all Trading listings -> click Recent Trades -> read all trades -> show both as tables. Data analysis modules were retired. The only model that may choose browser actions is Jev (TypeSafe), with one mechanical exception: `Agent(finish_phase_after=(label, n))` (`site.phase_finish_rule`) ends a phase without asking Jev once the action named `label` (Load More) ran `n` times in that phase; it is logged in `state["rule_events"]` and shown in the decision log. The same rule also runs the loading cycle inside a phase (`Agent._next_by_rule`): after Load More it scrolls to the bottom, after scrolling to the bottom it presses Load More if that button is on the page; otherwise (first step of a phase, no button) Jev chooses. The finish half is also re-checked at the start of every
`predict`, before the page read, so a press whose page read went stale still ends its phase there instead of costing a
read and a Jev call. Rule steps have `model_calls = 0` and appear in `rule_events` with `press: True`. Apart from the table jump and the base rule (`stripToBase`) below, rules never choose search, product or tab targets; do not add any other LLM call, in particular no LLM-based data analysis and no model that generates field text.
- Finding the product (extension, `extension/src/traderie/finder.js`) has three layers, one attempt each: (1) table jump: the English name is in `extension/src/traderie/data/items.json` -> the program opens `/product/<slug>` itself, with no Jev call, then checks the page title is that item (otherwise layer 2); this is the only place the program chooses a product, and it never chooses anything else; (2) search: Jev types the name that the program supplies and picks the result; the program cleans the text first and never lets Jev rewrite it; (3) base list: only when the search page says "No results could be found" for a well-formed name, the plain item type comes from the fixed `bases` list (program rule first, see the next bullet, otherwise Jev picks one or none through `pick_base`, `POST /api/run/base`), then one more search with that name; no pick means "not found" and the run ends. The base list is a fixed option list; it never filters the page's element list. The result page always says which layer found the item, and a base result says the quality was not filtered. Chinese names are translated through the same table (`zh`); a Chinese name that is not in it fails before the quota is used. Names shared by two products (`Crescent Moon`, `Ward`, `Wirt's Leg`: `ALLOWED_DUPLICATE_KEYS` in `scripts/audit_item_tables.py`) are ambiguous: no table jump, search decides.
- Program-side base rule (sanctioned exception, `stripToBase` in `extension/src/traderie/lookup.js`; mirrors the table jump): in layer 3 the program first drops leading quality words one at a time ("Rare Ring" -> "Ring") and takes the first remainder that is an exact entry of the fixed `bases` list. A match is sent as `base` to `POST /api/run/base`, which only checks it against the server's list and swaps the run token: no Jev call. Only when nothing matches does Jev pick from the list (`pick_base`: one request, split into several questions when the list is long). The rule chooses search text from a fixed list, never an element or a click, and does not filter the element list. Model calls per lookup: table jump 0; search = the Jev calls of the Agent loop (`choose` may re-ask once, both requests count in `usage`); base layer 0 (rule matched) or 1 (`pick_base`). All of them share one budget of 30 Jev calls per run (`JEV_CALL_LIMIT` in `extension/src/agent.js`, `MAX_MODEL_CALLS` in `services/jevsvc/app.py`); the core demo has its own limits (60 actions, 120 decisions, `docs/design.md` Budgets).
- Stale-retry bound (extension, `extension/src/agent.js`): `STALE_RETRY_LIMIT = 3` — three consecutive `StalePage` failures on the same target (`choice`) on the same page fingerprint end the run as `blocked` with a Traditional-Chinese `scope_blocked_reason` (`連續 N 次都無法操作「<label>」（畫面沒有變化），查詢已停止`), a `rule_events` entry carrying `stale: true` and the count, and a matching `stale_events` line; any real change (a new page fingerprint, a different target, the page read that precedes a choice, or an action
that ran) clears `last_attempt` and resets the streak. When `Tab.overlayCover` (`src/jev_ultrafast/covered_overlay.js`, a read-only structural measurement: the failed target's centre is covered and the covering element's nearest positioned ancestor is `position: fixed` and covers at least 90% of the viewport) says a pop-up covers the target, the reason is instead the actionable 「有彈出視窗蓋住頁面…」 message; the measurement failing, or finding nothing, keeps the message above, and it never clicks or names a site element. It must stay: the click never executes, so no `history` entry is pushed, `MAX_STEPS` (which reads `history.length`) can never fire and `_finishPhaseByRule` counts only executed presses, so the mechanical loading rule could retry a covered element forever (measurements in `docs/design.md`). Related: `state.attempts` counts every action attempt (executed or stale) and `_prepareAction`'s bound is `history.length >= MAX_STEPS || attempts > MAX_STEPS` — keep both halves, or a covered element stops counting toward the step budget again.
- Challenge-guard precision (extension, `extension/src/traderie/site.js`): the bare word "captcha" counts as a challenge only when the page text is under `CHALLENGE_TEXT_MAX` and contains none of `TRADING_MARKERS` ("Trading For" / "Make an Offer", defined in `site.js`); the explicit signals ("just a moment" in the title, "verify you are human") and the `CHALLENGE_FRAMES` probe are unchanged. It must stay because the extension's `page.text` is snapshot text over the visible viewport only: a normal logged-in product page (measured 1998 chars) contains Traderie's own changelog line "Fixed captcha bugs when going between games", and the old word test made `sidepanel.js`'s `judge()` show 「Traderie 要求驗證或登入…防護頁/驗證碼」 instead of the run's real stop reason. The Python twin (`src/jev_ultrafast/traderie/site.py`) runs the same word test with the same `CHALLENGE_TEXT_MAX`, and only the `TRADING_MARKERS` half is absent there: its text is the whole-page `innerText`, so the short viewport snapshot the marker test protects (a real 1998-char listing page carrying the changelog line) cannot arise. The guard itself exists and is called on every read.
- Item tables (`items.json`) are a snapshot: regenerate with `uv run --group e2e python scripts/build_item_tables.py` (Windows only; starts the dedicated Chrome headless; Traderie blocks plain downloads). It builds `artifacts/item_tables_candidate.json` first and replaces the committed table, atomically, only if no category vanished or shrank by more than 10% (`--force` skips only that check) and `scripts/audit_item_tables.py` finds no problem (required categories and minimum counts, unique normalized names except the allow-list, slug format, base list, coverage floors, noise). `generated_at` only changes when the content changes. `--from-cache` rebuilds from `scripts/data/item_pairs.json` (commit it after a full run if it stays under about 300 KB; larger snapshots go to the git-ignored `artifacts/item_pairs.json`) without opening any website. The settings screen shows the table age (`tableAge`, stale after 90 days) and a table-jump miss note carries the running miss count; a stale table only loses the shortcut.
- Second search, yellow/blue/white items (extension, `extension/src/traderie/stats_flow.js`, `stats.js`, `properties.js`, `item-types.js`; form in `stats-form.js`; panel flow in `stats-query.js`): items without a fixed name are found by their affixes on the D2R home page ("Search All Stats"). This is a third program-side navigation, after the table jump and `stripToBase` (「TR交易」 below is the fourth, and the only one that writes to the site): the conditions the player switched on and confirmed in the form become the home page address (`?prop_<id>Min/Max=…`, `prop_Rarity=…`, `tags[]=…`), which the program opens and reads (first page only). No Jev; the only backend call is the one-use count (`runStatsFlow`'s `countUse` → `/api/run/start`, once the input is known good and before any window opens; a used-up or refused code ends the query there). Property ids and names are never written in code: they are read from Traderie's own property list from inside the player's Traderie tab (`GET /api/diablo2resurrected/properties?global=true`, kept in `chrome.storage.local` for 7 days; a failed read is an error, an old copy is never a fallback). The page's own **Item Type** list (the sidebar entries a base can be sent as) is cached the same way, for the same week (`extension/src/traderie/item-types.js`): a stored copy younger than a week skips step 1's home-page load altogether - and with it that load's own challenge check, which the filtered page's read still catches - while a failed read is an error that names the last good copy and never a fallback; an empty or challenged read is not stored. A condition with no, or more than one, matching property ends the query before anything is searched. Values that reach the address are checked to be digits. Affix lines of a screenshot are read by rules (`ocr/affixes.js`, dictionary `ocr/affix_dictionary.js`), never by a model, and only fill the form: a query never starts from a screenshot, the reader ticks the attributes it recognised and fills in the numbers it read, each marked in the form as coming from the capture for the player to confirm or edit (the reader misreads numbers, so the mark is the point; the player still presses start), and a ticked non-bool condition must carry at least one value (0 counts) before the search starts, while a bool condition needs none and ticking nothing at all stays legal. The base stays required, but the field offers the shipped item types as suggestions (`lookup.baseOptions` over `items.json`'s `bases`, filled when 模糊搜尋 mode is chosen; a suggestion, never a restriction), because a unique item's tooltip never names its base. The results line leads with what the rows it read are asking (min/median/quartiles of the High Rune Value, `traderie/price-summary.js`; unpriced rows are counted, never guessed) and then names where the query's input came from, typed or a picture or a scan record (`labels.sourceLine`, `panel-state.js`). Measured: this path has **no realised prices** — the affix filter URL has no recent-trades view (the filtered home page's 1037 links reach none of them and it carries only listing markers; the product page's `/recent` suffix on that URL lands on HELP with nothing in it), and trades exist only on a product page; see `docs/design.md`. The result is checked independently (`verifyStats`: home page, `filters_in_url`, `filters_shown`, `rows_match_filters`, rows read). `rows_match_filters` needs every listing to carry a card line for each number condition: each listing keeps its affix lines in `affixes` (`parseTradingTxt`; environment tags, quality words, `Classic` and variant words are dropped; `CARD_ENV_TAGS` (and `RECENT_ENV_TAGS`, its narrower twin on the recent-trades side) is the same list in `parsing.js` and `parsing.py`), and `conditionPattern` in `stats.js` turns the property name into the line it prints (`+{{value}}% Faster Cast Rate` -> `+8% Faster Cast Rate`). It runs on the rows the player sees (after the base display filter). Measured: Traderie did filter the list for unreachable numbers (life >= 99999 listed only charms whose life line is a joined range), so this is a guard against a page that lists everything, not a repair of a seen failure. The element list is not filtered by site vocabulary. `scripts/probe_stats.py` (read-only, needs the dedicated Chrome's Traderie login) re-measures the facts this relies on (list reachable, "and" between conditions, `Rarity` values, `tags[]`); its findings are in `docs/design.md`.
- Screenshot reader (extension, `extension/src/ocr/`): PP-OCRv6 small (Apache-2.0) runs in a side-panel module Web Worker through onnxruntime-web 1.30.0 (MIT); one engine only — WebGPU when `navigator.gpu` returns an adapter, otherwise wasm fixed at one thread. Only `ort.min.mjs`, the `ort-wasm-simd-threaded.jsep.mjs`/`.wasm` pair, `LICENSE` and `VERSIONS.json` ship in `extension/src/vendor/ort/`; `extension/src/vendor/ort/VERSIONS.json` records the pinned tarball and the size and SHA-256 of every vendored file, and `extension/test/ocr-vendor.test.mjs` recomputes them, so update both together and keep `.gitattributes` (`-text` for the vendor folder) so line endings never change the bytes. `manifest.json`'s CSP allows `'wasm-unsafe-eval'` (never `unsafe-eval`). The engine (`extension/src/ocr/engine.js`, whose `createEngineCache.keepWarm` keeps one warm) serves both the screenshot reader and the gear scan: `engineFor` creates the engine without warming it, the gear scan arms a synthetic warm-up pass through `keepWarm(..., { warmup: true })` on scan start to compile shaders before real crops arrive, while the reader's panel (`initOcrPanel`'s `holdEngine`) takes one `keepWarm(..., { warmup: true })` as soon as the models are stored (at panel start, or right after the first silent download in `downloadModels`) and never releases it: the engine is built and shader-warmed before any picture arrives and lives as long as the side panel, so no read pays the 0.7–1.3 s build or the +0.55 s first-inference shader cost and the 60 s idle timeout never fires for it (the worker is not terminated after about 60 s without a read while the panel holds it) (it still applies to a cache nobody holds). `createOcrEngine` serialises every worker request (`recognize`, `detectBoxes`, `warmup`) through one promise chain, so a read never runs on the det/cls/rec sessions while the warm-up does; a request queued behind one when the worker dies is rejected. `scripts/ocr_e2e.py`'s 穩定組 reads six screenshots twice in one panel session and gates the shown seconds minus the engine's `stages.total` (`WARM_GAP_MAX_MS = 400`, first read within `WARM_FIRST_EXTRA_MS = 300` of the median; measured 2026-10-22: median -1.5 ms, max 34 ms, first -3 ms); the per-reload A/B groups load the picture right after a reload, so their seconds include waiting behind the build and warm-up (the worst case, not the player's). `extension/src/ocr/models.js` downloads the four model files once into IndexedDB (~31.8 MB, `PPOCR_BYTES`), `extension/src/ocr/ppocrlib.js` runs the PP-OCR pipeline (det, cls, rec, and the lettering colour `inkTone`) and `extension/src/ocr/simplified.js` turns simplified glyphs back into traditional before matching. The reader's own read caps the detector's input for a **large picture** (over 1500 px a side: a phone photo) at the model's own side and cuts the recogniser's crops from the picture itself, which halves a phone photo's time without moving accuracy; screenshots and the scan's tooltip crops keep the model's policy exactly (`docs/design.md`, "The reader's phone photos"). The detector's boxes follow the reference's integer pyclipper offset (`clipperRoundOffset`, `detCandidateBox`; inflating the exact float rectangle put 14 of image-58's 21 boxes 1-2 px off and its name line read as "0-") and a crop the classifier turned is also read upright, the better score winning (`recognizeChecked`); both stay, pinned by `extension/test/ocr-ppocrlib.test.mjs` and measured in `docs/design.md`, "The name line read as 0-". The name-colour sampling `inkTone` is unchanged on purpose: a 1-2 px crop shift flips no class on the 54 pictures (measured 2026-10 on the earlier 54-picture set; the corpus is 50 pictures now, the four phone photos were removed from the working tree; this and the other 54 figures are historical) and the trimmed-mean and higher-floor variants were measured worse (`docs/design.md`, "Name-colour sampling"). Every read is head-first (`recognizeImage` in `ppocrlib.js`, `HEAD_LINES = 6`): the first six lines in reading order are classified and recognised first and reported through the worker's `head` message (`onHead`, engine option) before the rest is read, and the result still carries every line; nothing is read twice, a read of six lines or fewer has no head message. The reader (`panel.js` `decide`) decides the name on the head (filled in or asked) and decides again on the whole text only when the head was not sure; the scan (`processScanJob`) puts a record on the list at the head when it names the item or offers possible names and `session.finishRecord` completes it with the whole text, affix lines and the repeat check (a provisional record whose whole text reads as a listed item is removed and counted 略過); the whole text's own decision is the record's final one (a sure name replaces the head's, possible names turn a named record back into a question), so a scan record ends as it would have without a head, except that a name the player picked or typed meanwhile (`chosen`) is never replaced, a head refused as a repeat is counted once, and a read that fails after its head takes its head-only record off the list; the reader keeps a name its head was sure about, and does not decide again once the player has picked or typed a name; `perceivedLatencyMs` is the head's time then. The earlier `nameRegionOnly` option was never passed by any caller and is gone.
  - Unsure reads (`decideCandidates` in `extension/src/ocr/match.js`, shown by `ocr/panel.js`): the best candidate is filled into the name field by itself only when the read is sure — an item with no type line (base candidate) under it and a name longer than three characters, an item whose name line is printed in the colour of a unique, runeword or set item (`quality` gold or green from `extension/src/ocr/tone.js`, even with a type line under it; a name of three characters or less also needs that type line), or at most two type names (`base`); an item with a type line whose name line is yellow (rare), blue (magic), white or has no readable colour (a rare or magic item can print a random name equal to a catalogue name, and a unique prints the same two lines, so the name line's colour settles it only when it says gold or green) asks the player instead of filling anything by itself.
- Gear scan, a third navigation beside the name search and the affix search (extension, `extension/src/scan/`): for an online character whose equipment is in no local save, the player shares the D2R window once through Chrome's own dialog and hovers each item; the program never moves the mouse, sends no input to the game and has no global hotkey — it only reads the shared picture. `capture.js` takes frames with `getDisplayMedia` + `MediaStreamTrackProcessor` (never `requestVideoFrameCallback` or a timer, which stop or throttle while the game covers Chrome - measured 2026-10-13 with `scripts/scan_e2e.py --headed --minimize-after 20`: the window is minimized mid-sweep, so the side-panel page goes invisible the way it is when the game covers Chrome, and all four records still land); they are shrunk to `DETECT_WIDTH = 480` and a pure module finds the tooltip (`tooltip.js`): dark-pixel rows seed a band and a row or column inside it belongs to the panel through an inside-density window (a longest-run rule fails because the antialiasing on a text line breaks a row into 12..37 px pieces against the 48 px minimum), then `boxKey`'s content identity — the panel's own top square, 8×8 mean-grey cells quantised into 6 grey levels, matched within 12.5 % of the cells (measured: the same panel differs in 0..2 of the 64 cells, two different panels in 24..45) — makes the same panel shown again one crop. One engine, one read at a time, is what the scan runs — measured, two ORT WebGPU engines in one Chrome fail every read (「Session mismatch」), a second lane on wasm is 3-6x slower, and capping det's input for the scan's small crops cost a record's name on the fallback page: all three were built, measured and rejected in favour of the one-pipeline baseline (`docs/design.md`, "The 2 s target"). `session.js` is the state machine, and it freezes the identity of the picture it has cropped: that picture stays **held** while the detector's box stays within `HELD_BOX_PX = 6` px and its key stays within `HELD_KEY_TOLERANCE` (16 of 64 cells — deliberately twice accept's, measured: one panel differs in 0..4 cells across the sweep's eight positions and in 0..10 with its glyphs slid and the frame re-encoded, two different pictures in 23..38), so one hover is one crop, one read and one record however long the player holds the item and however much the game keeps re-rendering under it; the tooltip closing (`findTooltip` returns null) releases it, and so does deleting its record, which is what makes ✕ then the same hover record the item again. One item is one record: besides that key, a read whose whitespace-stripped OCR text is at least `TEXT_SAME = 0.6` alike an existing record's is the same item read again — character bigrams, and only when both texts are at least `TEXT_SAME_MIN = 40` characters, below which the texts must be equal — and is counted as 略過 rather than becoming a second record (measured on the 54 stored reads: two different items reach 0.449, the same tooltip read again from a second place reaches 0.689). The list is memory-only and disappears with the side panel, 清除紀錄 clears it, and CSV export works without ever running a query. Each record's 精準搜尋 starts the name query for the record's name at once (`onSearchName` -> `start()`); 模糊搜尋 starts the affix query at once with the record's base (its own name for a base record, else the **base candidate of the same read** - `scan/session.js` `baseCandidate`, the first `kind === "base"` of the candidates the matcher already returned - marked as coming from the capture), the quality from its name line's colour (`RARITY_BY_QUALITY`, else any) and **no affix conditions** (`statsForm.setForRecord`); a record with no base opens the affix form with the base box focused and starts nothing. The result screen's affix button (`panel-state.js` `affixHandoff(shown, source, ended, mode)`) reads 「用詞綴找同類」 after a name query that ended in a problem and 「加詞綴條件縮小範圍」 after an affix query; it opens `openAffixForm`, where the record's read affix lines are ticked and filled, marked as coming from the capture, for the player to confirm and start. a two-phase "name first" read (name region, then the rest of the same crop) was built and measured: it cut the scan's median latency about 30 % (1035-1078 -> 717-743 ms) but lost a name on the fallback page and produced duplicates on the hold page, so the scan reads each crop in one pass (`docs/design.md`, "Name first, then the rest"); the screen downloads what is missing by itself, silently (no on-screen notice, progress bar or 取消下載 button), and the models, engine cache and matcher are the screenshot reader's own (`extension/src/ocr/panel.js`), one engine and one download path. What the screen tells the player (`scan-panel.js`, measured 2026-10-14): when the side panel is covered (`document.visibilityState === "hidden"`) it says the scan gets slower and fast hovers may be missed (frames fall from about 10.7 to 3-4.8 per second and a crop's `convertToBlob` takes about 1-1.3 s there; a half-second hover was read 5 of 12 times against 12 of 12 with the panel visible); the slow-rate notice judges the last 6 seconds on the seconds that carried frames only (at least 3 of them, mean under 5; a second with no frame is a still picture, never "slow"); the status line says 「待辨識 N 件，約 M 秒」 (N × the average read, only after a read has landed); the stats line's 略過 counts a tooltip that gave no new record (the same panel by crop key, the same item's text read again, or nothing readable on it) and 丟棄 a tooltip lost because the 300-crop queue was full or because the browser could not encode its crop. Honest limitation, corrected 2026-10-14: the `*_slow` sim pages (`scripts/data/scan_sim_1080p_slow.html`, `scan_sim_1440p_slow.html`) draw the four tooltips at native size on a 1920x1080 / 2560x1440 canvas, but headless Chrome captures them at 800x396 / 800x360, so they do NOT exercise native size and "four records" on them proves nothing about a real 1080p/1440p capture (the earlier sentence saying they did was wrong). Measured offline on the 35 truth pictures drawn at native size (`docs/design.md`, "Gear scan": the detector at 480 wide misses about 17 % of them, 8 of 35 at 1080p, 15 plus 3 half-found at 1440p, 31 at 4K), a wider detector (`DETECT_WIDTH` 720 or 960) was tried and rejected (missed+half only 15 % / 9 % fewer, three false crops on a dark floor, 4x the cost): the same seven pictures fail at every width, so it is the detector's own logic, not resolution. The e2e's anti-throttle flags make a covered page still count as visible, so `scripts/scan_e2e.py` cannot see the covered-window slowdown at all (`--minimize-after` only shows the records still land on a hidden page). What a real D2R capture delivers (a smaller tooltip, a 4K capture, Windows display scaling) is not measured here. The first attempt at measuring native size was invalid for a plain reason worth remembering: the sim page resolves its picture paths relative to itself, so a variant placed anywhere but `scripts/data/` silently loads no pictures and records nothing.

## Architecture & Data Flow
```
goal -> demo.py (HTTP, loopback) -> controller.step (advance -> Agent tick -> advance again on error)
          predict: Browser.observe -> model.choose (TypeSafe) -> decision
          act:     history entry ("started") -> Browser.act (CDP input) -> observe -> "executed"/"unconfirmed"
        traderie/controller.advance() reads each view when the Agent finishes it, and runs before every step
```
- `src/jev_ultrafast/agent.py`: `Agent` is the only owner of `agent.state`. Commands: `predict`, `act`, `tick`, `handoff`. Status values: `ready`, `predicted`, `handoff`, `done`, `blocked`. A single-string goal on a Traderie D2R URL becomes a 2-phase plan (`trading`, `recent_trades`); finishing phase A sets `awaiting_handoff` and the controller must call `handoff`.
- `src/jev_ultrafast/browser.py`: one CDP session through `browser_harness`. `observe`, `fresh`, `act`, `evaluate`, `navigate`, `settle`, `close`. `fingerprint()` hashes url, text, actions and scroll. After a click, `observe` waits until the visible text has changed once (or 1.0 s passed) and then stayed unchanged for 0.4 s (cap 6 s; measured: 0.7/1.5 s gave a median loop of 26 s, 0.4/1.0 s about 16 s); `wait` sleeps 4 s so slow XHR content can arrive (a shorter wait made Jev answer `blocked` on half-loaded search results).
- `src/jev_ultrafast/snapshot.js`: runs inside the page. Garbage accessible names (`[object Object]`, `undefined`, `null`, `NaN`) are ignored and the visible text is used instead (Traderie ships `aria-label="[object Object]"` on listing links). Lists up to 250 visible safe elements as `e1..eN`, plus controls `scroll_down`, `scroll_up`, `scroll_bottom`, `scroll_top`, `wait`. Page text is capped at 6000 chars and only covers the visible viewport.
- Phases: `Agent.state["phase_start"]` is where the current phase began in `history`; `choose` receives only that part, so `recent_actions` and `action_counts` (how often each action ran in this phase) restart at the handoff. The goal tells Jev to choose DONE when `action_counts` shows Load More at `LOAD_MORE_LIMIT` (counting from a list of actions was unreliable). Views carry `has_more` (a Load More button still on the page when it was read).
- `model.choose` asks Jev again, once, without the chosen operation when its target probability is below `MIN_TARGET_PROBABILITY = 0.5` (four same-name links once sent the Agent to another product page at 26%); the decision then has `reasked` and `model_calls = 2` and the usage sums both requests. `action_space` keeps at most `MAX_SAME_NAME_ELEMENTS = 2` elements with the same name and role (26 Min/Max boxes cost about 8% of the tokens). The Load More count (0-5, `site.validate_load_more`) comes from the demo selector (`reset` body `load_more`) or `--load-more`.
- `src/jev_ultrafast/model.py`: `post_json` (retries only network errors and HTTP 429/503/529), `action_space`, `choose`, `validate_choice` (checks probabilities only; there is no confidence anywhere). `questions.py` holds the prompt strings.
- `src/jev_ultrafast/config.py`: constants (`MAX_STEPS = 60`, viewport size), frozen `Settings` from `get_settings()`, `load_dotenv` (uses `setdefault`: the real environment wins over `.env`).
- `src/jev_ultrafast/demo.py`: loopback inspector on `127.0.0.1:8766`. POST checks Host, `X-Demo-Token` and Origin (403), single busy lock (409), `ValueError/RuntimeError/TimeoutError` -> 400. Commands: `reset`, `tick`, `report`; the page has one start button (「開始查詢」, runs `tick` until done), a stop button and the report button. `GET /api/report` returns the markdown; `GET /api/raw?view=trading|recent_trades` returns the stored page text (state carries only `text_length`; decisions other than the last are trimmed to a summary). Demo-owned fields live in `RUN` (`item_name`, `market`, `report_md`); never mutate `AGENT.state` from the demo.
- `src/jev_ultrafast/traderie/`: the Traderie domain.
  - `site.py`: URLs, `build_goal`, `LOAD_MORE_LIMIT = 2`, `product_root_url`, `traderie_scope_reason`, `detect_guard`.
  - `controller.py`: `new_market`, `read_view`, `verify_views`, `advance`, `run_agent`, `save_report`. Each view is read once, from the page the Agent is on (no navigation, no retry), into rows via `parsing.parse_trading_txt` / `parse_recent_trades`, and cross-checked against the page's own markers ("Trading For" / "They Give" counts: the trading side fails
    only on fewer rows than markers, the recent side on any difference). Status per view: `NOT_RUN`, `PASSED`, `FAILED`, `BLOCKED`.
  - `verification.py`: `read_settled_page`, `matches_item`. The 8 independent checks live in `controller.verify_views`: `product_page`, `item_match`, `same_product`, `trading_view`, `recent_view`, `trading_rows_ok`, `recent_rows_ok`, `not_blocked`.
  - `parsing.py`: rule-based readers, no AI.
  - Retired analysis code, helper scripts and the old OCR project are no longer in the tree.
- `src/jev_ultrafast/static/`: `index.html` (token placeholder `__TOKEN__`), `app.js`, `style.css`, `csv.js` (CSV export, no DOM access, tested through node), `tokens.css` (the shared design tokens, colour and metric (spacing, radius, control heights): the names and the panel's values; `extension/build.py` copies it next to `sidepanel.css`, which uses it, while the demo still declares its own palette in `style.css` - `tests/test_ui_tokens.py` keeps that honest). Results are two columns (listings 3fr, trades 2fr) at >= 1000px, stacked below; `marketViews.trading.mergeInto` shows the high-rune column as small text under the price only in the wide layout (CSS `.col-merge`/`.inline-extra`), CSV still exports all columns. Three tab panels: `tab-run`, `tab-results`, `tab-usage` (all element ids must stay in `index.html`; `tests/test_ui_static.py` checks this). The page switches to the results tab once when `market.verification` appears, unless the user picked a tab. It shows the same table columns as the panel and the same sentences for a failed check, each a copy the page carries because the two cannot share code, kept in step by `extension/test/columns-parity.test.mjs` and `extension/test/check-reasons-parity.test.mjs` (a failed run must never print an identifier like `same_product` to a non-technical player). Page text is untrusted: write table cells with `textContent`, never `innerHTML`; CSV cells starting with `= + - @` get a leading apostrophe.

## Code Conventions & Common Patterns
- Python >= 3.12, ruff line length 120, rules `E,F,I`. Clean cutover: when removing a behavior, migrate every caller and delete dead code; no shims or aliases.
- Safety patterns to keep:
  - `Agent` consumes a decision once, before any mutation or model call.
  - `StalePage` triggers a re-observe and a new decision, never a replay of the action.
  - `Browser.fresh(page, action)` guards element actions (including `fill`); page-level `MARKER` is used for page-level actions.
  - Scope guard (`traderie_scope_reason`) blocks anything outside Traderie D2R.
  - Verification results always carry a human-readable reason (`view_reasons`, `failed_checks`).
- Errors: raise `ValueError` for caller mistakes, `RuntimeError`/`TimeoutError` for browser or network problems; the demo maps them to HTTP 400.
- Config: read through `get_settings()`; never read secrets in the frontend.
- Naming: snake_case modules and functions; test functions are full sentences (`test_stale_decision_is_consumed_before_any_mutation`); status strings are upper-case constants (`PASSED`, `BLOCKED`).

## Runtime/Tooling Preferences
- Python with `uv` (lock file `uv.lock`; dependency groups `dev` and `e2e`); `node` for `node --check` on the demo scripts and `node --test` for the extension tests. No CI directory.
- By default `src/jev_ultrafast/chrome.py` starts a dedicated headless Chrome (port 9355, profile `src/.tmp-jev-chrome` next to the package, git-ignored) and points `browser_harness` at it with a per-process daemon name (`BU_NAME=jev-<pid>`). `JEV_CHROME` selects the mode: `headless` (default), `window` (visible dedicated Chrome), `existing` (the user's own Chrome; needs remote debugging on port 9222, and if Chrome asks "Allow remote debugging?", only the user can click Allow).
- Only in the dedicated Chrome: advertising/tracker hosts are blocked (`BLOCKED_HOSTS`, halves memory), picture URLs are blocked when screenshots are off (`Browser(images=False)`; the demo keeps pictures for its screenshot panel), the page cache is capped at 50 MB, small caches are removed on close (the login stays), and renderer processes are limited. In headless Chrome the tab must be a foreground tab or screenshots hang.
- TypeSafe requires `TYPESAFE_API_KEY`. No local text model is needed.
- Without a login, Traderie hides Load More and may block Recent Trades. Tell the user to run `uv run python scripts/login.py`: the window now stays open until the login is actually detected (it polls `LOGGED_IN_JS`: host `traderie.com` and `readyState === "complete"` and a non-empty body and no `Log In` link left), pressing Enter only ends the wait early and the wait no longer depends on it, `JEV_LOGIN_WAIT_SECONDS` (default 600) bounds it, and reaching the bound prints a clear Traditional-Chinese message and exits 1; the old bare `input()` ended instantly on a stdin that cannot wait (EOF or redirected) and the window closed before the human could log in. In `existing` mode, log in in the user's Chrome instead.

A record's search buttons start real queries, so the script proves a start with a stub instead of a query: before the clicks the panel's `/api/run/start` fetch is counted and answered, and `chrome.windows.create` is counted and refused (a started query ends in the problem 「無法開啟查詢視窗」); `--shots` also writes the screens at 320/360/400 px to `artifacts/scan-e2e/shots/` and fails on a sideways scroll.

## Execution Strategy

- **Highly parallel.** Split work into independent modules that share neither a file nor a resource, and run modules that share nothing at the same time. Prefer many focused agents over a single serial agent.
- **Use vibe sessions.** In this harness that means `good` for design, debugging and multi-file work, and `fast` for mechanical work. `fast` is currently unusable because its model is end-of-life, so use `good` instead.
- **Serialize anything that shares a resource.** The shared resources here are the dedicated Chrome (`src/.tmp-jev-chrome`, `extension/dist-e2e`) and `extension/dist`. Only one agent may run a Chrome-based end-to-end script at a time; the family is `scripts/ocr_e2e.py`, `scripts/extension_e2e.py` and `scripts/extension_batch.py`, sharing `scripts/_cdp.py` as their CDP client, and `scripts/scan_e2e.py` belongs to that same family. `scripts/demo_e2e.py` belongs to it too even though it drives the *demo's* Chrome (port 9355): it must not run while the demo, the CLI or another member is running. No agent may call `free_profile()` on its own or kill a Chrome it did not start; only a Chrome end-to-end script of that family may clear the profile (at its own startup, and only while no other agent is using the dedicated Chrome), and two agents must never edit the same file.
- **Keep going** until every executable task in the plan is done or a real block is hit. Before reporting a block, exhaust the available tools and data; one failed check is not a block.
- **Verify each finished module immediately** with the check that belongs to it: `node --test "extension/test/*.test.mjs"`, `uv run pytest`, `uv run ruff check .`, `uv run python extension/build.py`, and — for anything that changes the screenshot reader's accuracy — the live `uv run --group e2e python scripts/ocr_e2e.py` with both gate groups matching. The strategy's server-stack rule maps onto the dedicated-Chrome serialization above, and this repository has no `lunia_ops.py`, `golden 11/11`, `e2e_warm.py` or `loadtest.py`.
- **Things only the user can do** (acting inside the game, pressing UAC, deciding a switch): stop and give step-by-step instructions; never assume it is already done.
- **Anything that can be done on the user's behalf: just do it.**
